Nearly everything I find is the same bug in a different system. A check reports success when it never actually looked.

A prompt-injection filter covered six of the seven methods that needed it. A fuzz harness opened the file and closed it again without ever reading an attribute. An admin screen reported no access while the write went through. A safety probe passed green while the agent sent data out on every turn. Four different codebases, one failure: the thing meant to catch the problem could not have seen it.

I look for that gap, report it to the vendor privately, and then write up what the test missed and how I proved it was missing. Software engineer in Beirut, working on MCP servers and agent tooling. US citizen, no sponsorship needed.

Writeups

Each of these went to the vendor privately first. Each one includes what I got wrong, because in every case the mistakes were the part worth reading.

One method of one tool: an incomplete content filter in github-mcp-server lockdown mode

pull_request_read dispatches nine methods from one switch. Seven of them return text written by repository users, and lockdown mode covered six. The two-account rig and the positive control that proved it at runtime, why the vendor's framing of lockdown was right and mine was wrong, and five other things I got wrong in the report.

Reported Aug 2026, fixed in v1.10.0 the same month. One of three credited reporters.

A one-byte differential in netcdf-c: integer overflow in classic-format length arithmetic

netcdf-c runs on OSS-Fuzz, and the only harness it had opened a file and closed it without ever reading an attribute value. One byte of an 80-byte header undersizes a heap allocation while the un-wrapped element count still drives the read loop. Includes the half of my hypothesis that was wrong, a claim I had to retract in public, and the maintainer's observation that my own fix ships no regression test.

Reported Jul 2026. Fix PR open at the maintainer's request. How to build a triggering file is not published here.
