Three reports to Keycloak, and what separated them

Mahdi Alhakim

In early August 2026 I sent Keycloak three private security reports. All three were accepted, made public by Keycloak staff, and credited to me by name. None got a CVE. One was reclassified as an enhancement, one as a weakness handled publicly as a hardening improvement, and one as a bug, fixed, backported and released.

This is a writeup about that: three reports to one vendor, what separated the one that stayed a bug from the two that did not, and what I would change about how I write a severity argument. More of it is about the reports than about the bugs.

What decided each label was whether Keycloak already had a rule that the behavior broke; impact had little to do with it.

The three, with their public records.

All three were originally tracked in Keycloak's private security repository and migrated into the public tracker by staff, which is why each public issue is opened by a Keycloak employee and carries an acknowledgment line instead of being filed under my own account. The fixes were written by Keycloak maintainers in every case except #51720, which is mine and is not merged.

The one that stayed a bug

ClientPermissions.isInternal decides whether a client is off limits to fine-grained admin permissions. It denylisted the realm-management client, and in the master realm any client whose id ends in -realm. It did not denylist admin-permissions, which is the resource server that holds the realm's entire fine-grained permissions model.

So a delegated administrator holding a Clients:manage permission and no realm-management roles could update and disable that client through the Admin API. Set serviceAccountsEnabled, add redirect URIs, turn on direct access grants, rename the clientId. Deleting it was correctly refused.

This one stayed a bug because the product already disagreed with itself. getAccess, the endpoint that tells an administrator what they are allowed to do, special-cased this client and returned manage: false. canManage, the enforcement path, did not have the same check and fell through to the generic permission evaluation, which granted the write. The access report said no and the enforcement said yes.

I reported it with the smallest fix I could find: add the constant for that client id to isInternal, which is how realm-management is already handled. I also wrote in the report that no privilege escalation results from it, because enforcement resolves clients by internal id rather than by clientId, and disabling the client does not relax the reporting admin's own restrictions.

Keycloak kept it as kind/bug with priority/important and fixed it in the place I named. The merged change is the maintainers' own and goes further than mine: it adds coverage on the enforcement path and on the access report, so the two cannot drift apart again. Two community pull requests proposing the same one-line change appeared on the public issue and were closed unmerged. The change that landed was written with tests.

It was backported the next day, about 31 hours after it reached main, and shipped in Keycloak 26.8.2 on 2026-11-05.

The one that became an enhancement

Keycloak's Shared Signals Framework support emits a CAEP session-revoked Security Event Token when a session ends by logout. It emitted nothing when the same session ended by OAuth2 token revocation. The /revoke endpoint removes the user session server side, but the event mapper mapped only LOGOUT to that token type, and REVOKE_GRANT mapped to nothing.

The consequence depends entirely on how a relying party validates. A party that introspects every request notices immediately. A party that validates access tokens offline, which is the normal and recommended pattern, and that subscribes to CAEP specifically so it can learn about revocation in real time, is never told. It keeps honoring already-issued access tokens for that session until they expire.

I filed it as CWE-613, insufficient session expiration. Keycloak accepted the behavior, labeled it priority/important, fixed it on main, and reclassified it as kind/enhancement.

The reclassification is correct, and the reasoning is already in the issue, in text from my own report: the exposure window is bounded by the access-token lifetime, and the ssf feature is experimental and off by default. Keycloak relabeled the issue on 2026-10-07 without a comment, so this is my reading of the decision. A window bounded by a configured token lifetime is a delay the deployment chose for itself, and an experimental feature that is off by default makes no promise yet.

My report described relying parties continuing to accept revoked tokens, which also happens with no CAEP at all. CAEP shortens that window, and the defect is that it did so for logout but not for /revoke. That makes it an enhancement to an experimental feature, which is how Keycloak classified it.

The fix merged to main on 2026-10-07 and was not backported. It is labeled for 27.0.0, which has not been released.

The one that became a hardening improvement, and the fix I wrote for it

The JWT authorization grant accepts an assertion from a federated identity provider and exchanges it for an access token. The audience binding is what stops an assertion issued for one relying party from being replayed at another. Keycloak reads the acceptable audiences from a client attribute, oauth2.jwt.authorization.grant.audience. When that attribute is present it replaces the server-computed default, which is the realm issuer and the token endpoint, rather than narrowing it. The same holds for the identity provider allowlist attribute.

Separately, the dynamic client registration write path copies every key from the submitted attribute map without inspecting any of them, and no client-registration policy inspects client attributes.

Put those together and a self-registered client can set its own audience allowlist to the audience of a different relying party, set its own identity provider allowlist, obtain an assertion issued for that other party, and exchange it for an access token for the federated user.

I filed it as an authorization problem. Keycloak labeled it kind/weakness and wrote the reason into the public issue: the custom audience mapping is an administrator-level configuration that is by design available at the client level, so it is handled publicly as a hardening improvement and not as a vulnerability.

The classification fits, and the reason is structural. The attribute is a configuration knob that an administrator is supposed to be able to set. There is no rule in the product saying a client may not have a custom audience list, so nothing is being bypassed when a client has one. The actual defect is narrower: dynamic client registration lets a client write a knob that was only ever meant to be set for it. The audience replacement makes it worse, but the defect is that registration lets a client write the attribute.

The distinction decides where the fix goes. If the problem is the audience semantics, you change the grant to intersect with the provider default, and you break every deployment that relies on replacement. If the problem is who may write the attribute, you gate the write, and that breaks nothing. My first version of the fix was a hard-coded check in the registration provider. In review, a Keycloak maintainer (mposolda) pointed me to client policies, the mechanism Keycloak already has for gating exactly this kind of write, and I rebuilt it that way.

PR #51720 now adds a client policy executor, jwt-authorization-grant-settings-disabled, that rejects requests changing either of the two attributes. It follows the existing FullScopeDisabledExecutor, handles both REGISTER and UPDATE so dynamic registration and the Admin REST API are both covered, and rejects only an actual change: an update sends the whole client representation back, so a request repeating a value the client already has still passes and unrelated edits keep working. Enabling the grant on an existing client is rejected, turning it off is allowed. Combined with the existing client-updater-context condition, the policy can be scoped to the client's own requests, leaving administrators free to configure the client normally. Six files, 664 lines added, one removed, eleven integration tests, and documentation in both the securing-apps guide and the client-policies reference next to the sibling executors.

The pull request states one limit: client policies only bind the paths that fire client policy events, so realm import and partial import are not covered. Both require manage-realm, which can disable the policy anyway, so the gap does not reintroduce the original problem, but it is a gap. The executor is also opt-in, like every client policy, so it hardens a deployment that enables it and does nothing for one that does not.

It has been open since 2026-08-13. On 2026-10-23 a maintainer (lhanusov) asked for one more rebase and said he would then do a final review and ask for merge; I rebased that day. It is not merged yet.

I also disclosed in the pull request body that I used AI agents to help analyze the code paths and draft the change, and that I reviewed and verified all of it.

What separated the three

The classes the vendor assigned do not track impact. The admin-permissions bug was the one I explicitly told the vendor had no privilege escalation in it, and it is the one that got fixed as a bug and backported the day after it reached main. The audience one has the most alarming attack narrative of the three and is the one still labeled a weakness.

What separated them is whether the product already contained a rule the behavior violated.

  • #51630 violated one. getAccess said manage: false. The product had stated the intended answer and the enforcement path gave a different one. That is a bug in the ordinary sense and needs no severity argument at all. I only had to show two functions that disagreed.
  • #51718 did not. Nothing in Keycloak said a client may not have a custom audience list. I was asking for a rule that did not exist yet, which is a hardening request no matter how I phrase it.
  • #51376 was in between. The rule existed, in the sense that CAEP has a defined meaning, but it existed in an experimental feature that is off by default, so the product had not yet promised it to anybody.

None of that is specific to Keycloak. A report that says "these two code paths in your product disagree about the same question" is almost impossible to argue with and needs no CVSS vector. A report that says "this configuration surface should be narrower than you made it" is a design opinion, and calling it a bypass backfires, because the vendor spends its first reply on the framing instead of the fix.

What I would do differently

The habit I would change is to say which rule is broken, in the product's own words, before saying how bad it is. On #51630 I did that by accident, because the contradiction was so visible that naming it was the shortest way to describe the bug; on the other two I led with impact and let the rule be implied, which is backwards. If I cannot point at a statement the product makes and show the code not honoring it, I am proposing a new rule, and I should say so plainly and argue for it on its merits.

The habit I would keep is stating the mitigating facts in the report before anyone asks. #51630 says in my own words that no privilege escalation results; #51718 notes that assertions carrying more than one audience are refused and that assertions are single use, which limits exploitation without preventing it; #51376 notes the exposure window is bounded. Every one of those is evidence against my own severity, and a triager who finds a limiting fact you omitted discounts everything else you wrote.

I did not argue either reclassification; both were accurate, and all three issues are fixed or have a fix open. I sent a fix wherever I could tell where it went.

What I do not know

Whether any of these were reported by someone else first. The private reports were acknowledged and the public issues credit me by name, but Keycloak's private tracker is not visible to me and I have not tried to reconstruct it.

The exact date I sent each report. I did not keep the send timestamps; the dates staff opened the issues (2026-08-03, 2026-08-11 and 2026-08-13) are upper bounds on when each report went in.
