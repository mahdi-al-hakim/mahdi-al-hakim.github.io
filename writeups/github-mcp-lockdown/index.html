One method of one tool: an incomplete content filter in github-mcp-server lockdown mode

Mahdi Alhakim

github/github-mcp-server ships an opt-in flag, --lockdown-mode, whose job is to keep text written by people with no push access to a public repository out of an agent's context. It is a prompt-injection mitigation. pull_request_read is a multi-method tool: one tool name, a method argument, nine cases in a switch. Seven of those nine return text written by repository users, and lockdown was applied to them one case at a time. Six had a check. get_commits did not, so under lockdown a fork pull request from an untrusted account still returned its commit messages in full.

That is the whole bug. The rest of this is the trust model it sits in, how the gap was found, how it was proven at runtime instead of read off the source, and where my own report was wide of the mark.

Status. Reported privately on 2026-08-09. Fix merged as PR #3109 at 12:41 UTC on 2026-08-19 (merge commit 769340d6) and published in v1.10.0 at 17:36 UTC the same day, tracked publicly as issue #3105. The fix was written by a maintainer, not by me; I reported the gap and sent a tested patch. The PR body names three reporters and I am one of them. There is no CVE and no published advisory. GitHub did open a draft advisory for it, GHSA-w8ww-p3c7-hwxc, titled "Lockdown mode does not restrict pull_request_read get_commits, exposing untrusted fork pull request commit messages". It was closed without publication, so it carries no severity and no CVE, and it is visible through the repository's security-advisories API rather than on the advisory site. I mention it only because it is the vendor's own wording for the finding. Everything below is either in that public record or is my own evidence against the shipped v1.8.0 binary using two accounts I own.

This is not an authorization bypass, and the distinction does real work. The vendor's position, written into the project's own documentation as part of this fix, is that lockdown is a best-effort content filter and explicitly not an authorization boundary. I filed it as missing authorization. That was wrong, and the section near the end says how.

What lockdown is for

The rule is per item. For each piece of content the server is about to return from a public repository, check whether its author has push access, and if not, withhold it or filter it out. Private repositories are unaffected. Collaborators keep full access to their own content.

The point is narrow and worth stating precisely, because the severity argument turns on it. An agent calling these tools already holds a credential. That credential can read every one of these public objects directly through the GitHub API. Lockdown does not take that away and was never trying to. What it tries to do is stop the server from handing an agent free text written by a stranger, because an agent treats text in its context as information and sometimes as instruction. The threat is not disclosure. The threat is that the model reads it.

So the control is a filter on an input channel, and the only property that matters about a filter on an input channel is whether it covers every entrance.

The gap

It covered six of the seven. Here is the enumeration as it stood at v1.8.0, which is the version I confirmed against. The function names and the line numbers are from the public source at that tag.

method function lockdown at v1.8.0
get GetPullRequest authorLockdownResult inline, whole result
get_diff GetPullRequestDiff enforcePullRequestLockdown, whole result
get_files GetPullRequestFiles enforcePullRequestLockdown, whole result
get_commits GetPullRequestCommits none
get_comments GetIssueComments IsSafeContent per item
get_review_comments GetPullRequestReviewComments IsSafeContent per item
get_reviews GetPullRequestReviews IsSafeContent per item
get_status GetPullRequestStatus none; returns CI status, not pull request text
get_check_runs GetPullRequestCheckRuns none; returns CI check data, not pull request text

The seven rows above the line are the methods that return text authored by repository users. That is the enumeration the filter had to cover. The last two return data produced by the CI system rather than by the pull request author, and I did not examine them.

Three things in that table are worth more than the one missing row.

The same check is spelled three ways. get calls authorLockdownResult directly, because it already holds the pull request object and does not need to fetch it again. get_diff and get_files call enforcePullRequestLockdown, which fetches the pull request and then calls the same helper. The comment and review methods call IsSafeContent per entry. One policy, three call shapes. Grepping for any single one of them tells you nothing about coverage.

The check is at the call site, not at the exit. There is no point through which content must pass on its way out of the server. Coverage is therefore a property of whether each author remembered, and a new content path is a new place to forget.

The tool surface is wider than the tool count. pull_request_read is one entry in the tool list the model is shown and one entry in the registry the maintainers maintain. It is a dispatch table with nine cases. You cannot see coverage of a dispatch table from a tool list.

And a commit message is free text. Any GitHub user can put anything in one, on a branch in their own fork, with no review and no interaction with the target repository beyond opening the pull request.

What it actually buys an attacker

Nothing new to read, and nothing new to write. The operator's token could always fetch that commit message. No permission changed and no boundary moved.

What it buys is placement. An operator who turned lockdown on has decided that fork content is untrusted input for this agent. With the flag on, get_diff refuses and strangers' comments disappear, so the remaining text in the agent's context looks like text the operator sanctioned. The commit message arrives in that same context with the same apparent provenance. It is also the least-watched free-text field on a pull request: nobody reviews commit messages, and no human workflow renders them prominently.

The ceiling is whatever the consuming agent will do with instructions it believes came from the repository it is working in. That is a property of the agent, not of this server, and I had not surveyed it. Which is one reason the score I attached to the report was weaker than I made it sound.

How I found it

Not by fuzzing. The hypothesis came first, and it was about the shape of the code and not about this repository: a filter that must be applied by hand at each call site, sitting behind a dispatch table, will be applied at some of the sites. That is an incomplete-enumeration bug. The way to find one is to list the enumeration and walk it, not to test the control on the path the documentation uses as its example.

So the method was mechanical.

  1. Find the gate. enforcePullRequestLockdown and authorLockdownResult in pkg/github/pullrequests.go, IsSafeContent in pkg/lockdown/lockdown.go.
  2. List every case in the pull_request_read dispatch that returns text a repository user wrote.
  3. For each case, follow the call into the function that does the work and check whether any of the three gates appears in it.
  4. For every case where none does, establish whether the text really is attacker-writable, and prove it at runtime rather than from reading.

Step 3 produced one hit, and it produced it from the function signature alone. All three gates need the dependency object that carries the lockdown cache. GetPullRequestCommits did not take that parameter at v1.7.0, v1.8.0 or v1.9.0, so no gate could have been called from inside it. The commit message reaches the caller through the minimal commit type's Message field with nothing in between.

I also checked when the gap opened, because an affected range you cannot defend is worse than no range. enforcePullRequestLockdown does not appear in pkg/github/pullrequests.go at v1.6.0 and does appear at v1.7.0, four times. GetPullRequestCommits lacks the dependency parameter at v1.7.0, v1.8.0 and v1.9.0. So the pull request gate and the gap in it arrived together, and the gap had never been covered.

Prior art, checked before writing anything up: the repository had exactly two published advisories at the time, GHSA-pjp5-fpmr-3349 (a lockdown singleton in HTTP mode causing cross-user client confusion) and GHSA-w4q6-qw23-4rg7 (a nil pointer dereference in the completion handler). Neither concerned get_commits.

The reproducer, and the control that makes it mean something

Reading the source tells you the gate is absent. It does not tell you the content is attacker-controlled in practice, and it does not tell you lockdown was even on. Both need a runtime test, and the second needs a control.

The rig used two accounts I own, no third party and no third party's data. A victim account owns a public repository and runs the server. An attacker account has no push access to it, forks it, and opens a pull request whose commit message carries a unique marker. The attacker also posts a comment with a second marker, and the victim posts a comment with a third. Then the same three methods are called twice, once with --lockdown-mode and once without.

The markers turn this into a measurement instead of an impression. COMMIT is the attacker's fork-PR commit message, HUMAN is the attacker's no-push comment, OK is the victim's push-access comment.

MODE: LOCKDOWN ON
  get_diff:     restricted=true   markers_present=[]        ("access to pull request is restricted by lockdown mode")
  get_commits:  restricted=false  markers_present=[COMMIT]  (attacker commit message returned)
  get_comments: restricted=false  markers_present=[OK]      (attacker no-push comment filtered; victim comment kept)

MODE: lockdown OFF (control)
  get_diff:     restricted=false  markers_present=[]        (returns the diff)
  get_commits:  restricted=false  markers_present=[COMMIT]
  get_comments: restricted=false  markers_present=[HUMAN,OK]

That ran against the shipped v1.8.0 release binary, not a build of my own, driven by a short MCP stdio client that speaks JSON-RPC to the server and greps the tool results for the three markers.

Read the two blocks together, because neither is informative alone.

  • get_diff refusing with the flag on and returning the diff with it off proves lockdown was active in the first run. Without that line, "get_commits returned the commit" is equally consistent with lockdown being off, with the flag being misspelled, and with the fork not being detected as a fork.
  • get_comments dropping HUMAN with the flag on and keeping both comments with it off proves the per-item filter was working on this exact pull request against this exact non-push author. So the push-access lookup resolved correctly and the attacker really was classified as untrusted.
  • Against those two, get_commits returning COMMIT in both runs is the finding. Same object, same author, same classification, same process. One method returns the text and its siblings do not.

The positive control is the only reason the negative results are informative. It is the difference between "lockdown missed this method" and "I probably ran it wrong".

The fix, and verifying it

Three lines of substance, deliberately boring.

  1. Give GetPullRequestCommits the dependency object.
  2. Call the existing enforcePullRequestLockdown at the top of it and return early if it refuses.
  3. Pass the dependency object at the one dispatch call site.

No new code path. It reuses the gate get_diff and get_files already shipped, which is the version of this fix with the smallest surface for a new mistake.

I built and ran that change before sending it, because a suggested fix that has not been run is a suggestion and not evidence. Against the then-current source with Go 1.26.5: go build clean, go vet clean, pull-request unit tests passing. One unrelated test failed on a tool-schema snapshot, caused by a trailing carriage return in base64 icon data, which is a line-ending artifact of my Windows checkout. I proved it pre-existing by stashing the patch and getting the identical failure on the unpatched baseline, and said so in the report rather than leaving a red test unexplained.

Then the same two-account rig again, across the four states that matter.

Build Lockdown PR author get_commits Meaning
unpatched on no push access restricted=false, [COMMIT] the bug
patched on no push access restricted=true, [] fixed, matches get_diff
patched off no push access restricted=false, [COMMIT] no regression with the flag off
patched on push access restricted=false, [COMMIT] no over-restriction

The last row is the one people skip. A fix that also breaks the legitimate case is not a fix, and "restrict everything" would have passed the first three rows.

Blast radius: GetPullRequestCommits had exactly one caller, the dispatch case that was updated. With lockdown off the gate returns before issuing any request, so the off path is unchanged.

What I did not verify, and said so in the report: the cross-platform matrix, HTTP mode, the GraphQL paths, and every toolset combination. The maintainers' CI and review were the final gate, not my local run.

What the maintainers added that I had not

The merged mechanism is the one I proposed and tested. Two things went further, and both are worth reading if you care how vendors reason about this class of control.

The first is a design argument I had left implicit. Commits are a list with per-item author information, so per-item filtering was available, the way comments are filtered. The merged change deliberately keeps the whole-result check on the pull request author instead, on the grounds that every commit on a pull request belongs to the same untrusted head branch as the diff, so one check on the pull request author is both cheaper and strictly more conservative than filtering commit by commit. I agree, and I had not made the argument.

The second is documentation, and it is the part that corrected me. The merged change writes into the README and the configuration docs that lockdown mode is a best-effort content filter meant to reduce prompt-injection risk, that it is not an authorization boundary, that it does not restrict what the underlying credential can read or write, and that content withheld from a filtered tool response may still be reachable through other tools or the GitHub API with the same credential.

The documented list of methods that error under lockdown also grew to name get_diff, get_files and get_commits. Two of those were already implemented that way and simply undocumented. That is its own small lesson: the gap between the documented surface and the implemented surface is where this kind of bug lives in the first place.

What I got wrong

I filed it as missing authorization. My report classified it CWE-862 and described it as a bypass of a security control. On the vendor's framing, now in the documentation, the correct description is narrower and duller: one method of a multi-method tool was not covered by a filter that covered its siblings. The defect and the fix are identical either way. The severity story is not. "Authorization bypass" implies a boundary was crossed. Nothing was crossed, because the credential could always read that commit message through the API. What failed is that an agent was handed untrusted text by a tool configured to withhold untrusted text. That is a real problem for the agent and it is not an access-control problem.

I should have derived that myself from the fact that lockdown applies only to public repositories. A control that filters content the caller can fetch anyway by other means is a content filter by construction. I had the evidence for the right framing and reached for the wrong vocabulary, which inflates a report without adding anything to it.

I claimed it defeated "the stated purpose" of lockdown. The purpose was in fact stated loosely enough that part of the fix was to state it properly. Writing "defeats the stated purpose" put weight on documentation I had not checked was load-bearing.

I scored it with a user-interaction requirement. I rated it Medium, assuming the agent only reads the pull request when a user asks, which lowers the score. I flagged in the report that dropping the assumption raises it and left the choice to the triager. I still think submitting the conservative score was right, but my reasoning for it was weak: whether an agent reads a pull request unprompted is a property of the consuming agent, which I had not surveyed.

My affected range was wrong, and I am correcting it here. The report said >= 1.7.0, <= 1.8.0. That was true on 2026-08-09 and false by 2026-08-10, when v1.9.0 shipped with GetPullRequestCommits still lacking the dependency parameter. The correct published range is >= 1.7.0, <= 1.9.0, fixed in v1.10.0. I wrote a range pinned to the latest release at the time of writing and then never revisited it over the ten days before the fix landed. An affected range is a claim with a clock on it.

I do not know what the other two reporters reported. Three of us are credited on the fix. The public record does not break down who said what and I have not tried to reconstruct it. I was not necessarily first. This writeup is my own report and my own evidence only.

The transferable lesson

If a system filters untrusted text before it reaches a model, then the filter's coverage, not its logic, is the thing to audit. Three concrete versions of that.

Enumerate the dispatch table, not the tool list. Multi-method tools hide their real surface. One tool name with seven text-returning methods is seven places the filter has to appear. The registry says one tool. Count cases in the switch.

Grep for the policy, not for a function name. The same check here had three call shapes, one of which existed because the caller already held the object. A coverage audit that greps for one spelling reports coverage it has not checked. The reliable signal was the function signature: the gate needs a dependency the ungated function did not accept, which is visible without reading a line of the body.

Check the gate at the exit if you can. Applied by hand at each call site, coverage is a property of the author's memory. A filter that content cannot structurally avoid, applied where results are serialized, cannot be missed on a new path. That is a larger refactor than a bug fix and I did not propose it, but it is the difference between a control that is complete and one that is complete today.

Make the trust model explicit before arguing about severity. Most of the disagreement available in this finding is not about the code. It is about whether lockdown was a boundary or a filter, and the code was the same under both readings. Getting the vendor to write the answer down was worth more than the three lines of fix, because the next report against this surface starts from a stated model.

And one about reporting and not about agents: a negative result in a security test needs a positive control in the same run. "The attack did not work" and "the attack did not run" produce the same transcript. Here the control was free, because the sibling methods were already gated, so one extra call proved the rig was live.

Check it yourself

Everything in the coverage table and the version archaeology is public source at public tags. These are the commands.

# the merged fix, the credit line, and the design argument
gh pr view 3109 --repo github/github-mcp-server --json title,state,mergedAt,mergeCommit,body
gh pr diff 3109 --repo github/github-mcp-server

# the release that shipped it
gh release view v1.10.0 --repo github/github-mcp-server --json tagName,publishedAt,body

# the gap, at each affected tag: no dependency parameter means no gate could be called
for t in v1.6.0 v1.7.0 v1.8.0 v1.9.0; do
  gh api "repos/github/github-mcp-server/contents/pkg/github/pullrequests.go?ref=$t" \
    --jq .content | base64 -d \
    | grep -nE 'func GetPullRequestCommits|enforcePullRequestLockdown'
done

# prior art at the time of the report
gh api repos/github/github-mcp-server/security-advisories \
  --jq '.[] | select(.state=="published") | "\(.ghsa_id) \(.published_at) \(.summary)"'

The runtime transcript is not public, because it is a recording of two accounts I own. The rig is two accounts and a short script, so it is reproducible on demand and not something to take on trust.
