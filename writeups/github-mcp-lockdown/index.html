One method of one tool: an incomplete content filter in github-mcp-server lockdown mode

Mahdi Alhakim

github/github-mcp-server ships an opt-in flag, --lockdown-mode, whose job is to keep text written by people with no push access to a public repository out of an agent's context. It is a prompt-injection mitigation. pull_request_read is a multi-method tool: one tool name, a method argument, nine cases in a switch. Seven of those nine return text written by repository users, and lockdown was applied to them one case at a time. Six had a check. get_commits did not, so under lockdown a fork pull request from an untrusted account still returned its commit messages in full.

That is the whole bug. The rest covers the trust model it sits in, how the gap was found, and how it was proven at runtime.

Status. Reported privately on 2026-08-08 (UTC). Fix merged as PR #3109 at 12:41 UTC on 2026-08-19 (merge commit 769340d6) and published in v1.10.0 at 17:36 UTC the same day, tracked publicly as issue #3105. The fix was written by a maintainer, not by me; I reported the gap and sent a tested patch. The PR body names three reporters and I am one of them. There is no CVE and no published advisory. My runtime evidence is against the shipped v1.8.0 binary, using two accounts I own.

This is not an authorization bypass, and that changes the severity. The vendor's position, written into the project's own documentation as part of this fix, is that lockdown is a best-effort content filter and explicitly not an authorization boundary. I filed it as missing authorization, which overstated it.

What lockdown is for

The rule is per item. For each piece of content the server is about to return from a public repository, check whether its author has push access, and if not, withhold it or filter it out. Private repositories are unaffected. Collaborators keep full access to their own content.

An agent calling these tools already holds a credential. That credential can read every one of these public objects directly through the GitHub API. Lockdown does not take that away and was never trying to. What it tries to do is stop the server from handing an agent free text written by a stranger, because an agent treats text in its context as information and sometimes as instruction. Since the token can already read all of this, the risk is prompt injection: the model reading a stranger's text and following it.

So the control is a filter on an input channel, and the question is whether it covers every method that returns user-written text.

The gap

It covered six of the seven. Here is the enumeration as it stood at v1.8.0, which is the version I confirmed against. The function names and the line numbers are from the public source at that tag.

method lockdown at v1.8.0 function
get authorLockdownResult inline, whole result GetPullRequest
get_diff enforcePullRequestLockdown, whole result GetPullRequestDiff
get_files enforcePullRequestLockdown, whole result GetPullRequestFiles
get_commits none GetPullRequestCommits
get_comments IsSafeContent per item GetIssueComments
get_review_comments IsSafeContent per item GetPullRequestReviewComments
get_reviews IsSafeContent per item GetPullRequestReviews
get_status none; returns CI status, not pull request text GetPullRequestStatus
get_check_runs none; returns CI check data, not pull request text GetPullRequestCheckRuns

The seven rows above the line are the methods that return text authored by repository users. That is the enumeration the filter had to cover. The last two return data produced by the CI system rather than by the pull request author, and I did not examine them.

The table also shows how the filter was built.

The same check is spelled three ways. get calls authorLockdownResult directly, because it already holds the pull request object and does not need to fetch it again. get_diff and get_files call enforcePullRequestLockdown, which fetches the pull request and then calls the same helper. The comment and review methods call IsSafeContent per entry. Grepping for any one of them tells you nothing about coverage.

Each content path calls the check itself. There is no point through which content must pass on its way out of the server, so coverage depends on each author remembering to add the check to each new content path.

The tool surface is wider than the tool count. pull_request_read is one entry in the tool list the model is shown and one entry in the registry the maintainers maintain. It is a dispatch table with nine cases.

And a commit message is free text. Any GitHub user can put anything in one, on a branch in their own fork, with no review and no interaction with the target repository beyond opening the pull request.

What it gives an attacker

Nothing new to read, and nothing new to write. The operator's token could always fetch that commit message. No permission changed and no boundary moved.

What the attacker gets is a better position for an injected instruction. An operator who turned lockdown on has decided that fork content is untrusted input for this agent. With the flag on, get_diff refuses and strangers' comments disappear, so the remaining text in the agent's context looks like text the operator sanctioned. The commit message arrives in that same context with the same apparent provenance. It is also the least-watched free-text field on a pull request: nobody reviews commit messages, and no human workflow renders them prominently.

The ceiling is whatever the consuming agent will do with instructions it believes came from the repository it is working in. That is a property of the agent, not of this server.

How I found it

Not by fuzzing. The hypothesis came first, and it was about the shape of the code and not about this repository: a filter that must be applied by hand at each call site, sitting behind a dispatch table, will be applied at some of the sites. That is an incomplete-enumeration bug. The way to find one is to list the enumeration and walk it, not to test the control on the path the documentation uses as its example.

So the method was mechanical.

  1. Find the gate. enforcePullRequestLockdown and authorLockdownResult in pkg/github/pullrequests.go, IsSafeContent in pkg/lockdown/lockdown.go.
  2. List every case in the pull_request_read dispatch that returns text a repository user wrote.
  3. For each case, follow the call into the function that does the work and check whether any of the three gates appears in it.
  4. For every case where none does, establish whether the text really is attacker-writable, and prove it at runtime; reading the code is not enough.

Step 3 produced one hit, and it produced it from the function signature alone. All three gates need the dependency object that carries the lockdown cache. GetPullRequestCommits did not take that parameter at v1.7.0, v1.8.0 or v1.9.0, so no gate could have been called from inside it. The commit message reaches the caller through the minimal commit type's Message field with nothing in between.

I also checked when the gap opened. enforcePullRequestLockdown does not appear in pkg/github/pullrequests.go at v1.6.0 and does appear at v1.7.0, four times. GetPullRequestCommits lacks the dependency parameter at v1.7.0, v1.8.0 and v1.9.0. So the pull request gate and the gap in it arrived together, and the gap had never been covered.

Prior art, checked before writing anything up: the repository had exactly two published advisories at the time, GHSA-pjp5-fpmr-3349 (a lockdown singleton in HTTP mode causing cross-user client confusion) and GHSA-w4q6-qw23-4rg7 (a nil pointer dereference in the completion handler). Neither concerned get_commits.

The reproducer, and the control that makes it mean something

Reading the source tells you the gate is absent. It does not tell you the content is attacker-controlled in practice, and it does not tell you lockdown was even on. Both need a runtime test, and the second needs a control.

The rig used two accounts I own, no third party and no third party's data. A victim account owns a public repository and runs the server. An attacker account has no push access to it, forks it, and opens a pull request whose commit message carries a unique marker. The attacker also posts a comment with a second marker, and the victim posts a comment with a third. Then the same three methods are called twice, once with --lockdown-mode and once without.

COMMIT is the attacker's fork-PR commit message, HUMAN is the attacker's no-push comment, OK is the victim's push-access comment.

MODE: LOCKDOWN ON
  get_diff:     restricted=true   markers_present=[]
  # "access to pull request is restricted by lockdown mode"
  get_commits:  restricted=false  markers_present=[COMMIT]
  # attacker commit message returned
  get_comments: restricted=false  markers_present=[OK]
  # attacker no-push comment filtered; victim comment kept

MODE: lockdown OFF (control)
  get_diff:     restricted=false  markers_present=[]
  # returns the diff
  get_commits:  restricted=false  markers_present=[COMMIT]
  get_comments: restricted=false  markers_present=[HUMAN,OK]

That ran against the shipped v1.8.0 release binary, not a build of my own, driven by a short MCP stdio client that speaks JSON-RPC to the server and greps the tool results for the three markers.

Read the two blocks together, because neither is informative alone.

  • get_diff refusing with the flag on and returning the diff with it off proves lockdown was active in the first run. Without that line, "get_commits returned the commit" is equally consistent with lockdown being off, with the flag being misspelled, and with the fork not being detected as a fork.
  • get_comments dropping HUMAN with the flag on and keeping both comments with it off proves the per-item filter was working on this exact pull request against this exact non-push author. So the push-access lookup resolved correctly and the attacker really was classified as untrusted.
  • Against those two, get_commits returning COMMIT in both runs is the finding. The pull request, author, trust classification and server process were the same for all three calls; only get_commits returned the attacker's text.

The positive control is the only reason the negative results are informative. It is the difference between "lockdown missed this method" and "I probably ran it wrong".

The fix, and verifying it

Three lines of substance.

  1. Give GetPullRequestCommits the dependency object.
  2. Call the existing enforcePullRequestLockdown at the top of it and return early if it refuses.
  3. Pass the dependency object at the one dispatch call site.

No new code path. It reuses the gate get_diff and get_files already shipped, which is the version of this fix with the smallest surface for a new mistake.

I built and ran that change before sending it. Against the then-current source with Go 1.26.5: go build clean, go vet clean, pull-request unit tests passing. One unrelated snapshot test, a Windows line-ending artifact, failed identically on the unpatched baseline, and the report said so.

Then the same two-account rig again, across the four states that matter.

Build Lockdown PR author get_commits Meaning
unpatched on no push access restricted=false, [COMMIT] the bug
patched on no push access restricted=true, [] fixed, matches get_diff
patched off no push access restricted=false, [COMMIT] no regression with the flag off
patched on push access restricted=false, [COMMIT] no over-restriction

The last row checks that push-access authors still get their commits. A fix that blocked everything would have passed the first three rows.

Blast radius: GetPullRequestCommits had exactly one caller, the dispatch case that was updated. With lockdown off the gate returns before issuing any request, so the off path is unchanged.

What I did not verify, and said so in the report: the cross-platform matrix, HTTP mode, the GraphQL paths, and every toolset combination.

What the maintainers added that I had not

The merged mechanism is the one I proposed and tested. Two things went further.

The first is a design argument I had left implicit. Commits are a list with per-item author information, so per-item filtering was available, the way comments are filtered. The merged change deliberately keeps the whole-result check on the pull request author instead, on the grounds that every commit on a pull request belongs to the same untrusted head branch as the diff, so one check on the pull request author is both cheaper and strictly more conservative than filtering commit by commit.

The second is documentation. The merged change writes into the README and the configuration docs that lockdown mode is a best-effort content filter meant to reduce prompt-injection risk, that it is not an authorization boundary, that it does not restrict what the underlying credential can read or write, and that content withheld from a filtered tool response may still be reachable through other tools or the GitHub API with the same credential.

The documented list of methods that error under lockdown also grew to name get_diff, get_files and get_commits. Two of those were already implemented that way and simply undocumented. That is its own small lesson: the gap between the documented surface and the implemented surface is where this kind of bug lives in the first place.

Corrections to my report

Classification. My report called it CWE-862, a bypass of a security control. The accurate description is narrower: one method of a multi-method tool was not covered by a filter that covered its siblings. No boundary was crossed, because the credential could always read that commit message through the API, and lockdown applies only to public repositories, so it is a content filter by construction. What failed is that an agent was handed untrusted text by a tool configured to withhold it.

Affected range. The report said >= 1.7.0, <= 1.8.0. v1.9.0 shipped two days later with GetPullRequestCommits still ungated, so the correct range is >= 1.7.0, <= 1.9.0, fixed in v1.10.0.

The transferable lesson

If a system filters untrusted text before it reaches a model, audit which paths the filter covers. This finding turned up three concrete ways to do that.

The first is to enumerate the dispatch table rather than the tool list. Multi-method tools hide their real surface: one tool name with seven text-returning methods is seven places the filter has to appear, even though the registry reports a single tool, so the audit has to count cases in the switch. The second is to search for every spelling of the policy check. The same check here had three call shapes, one of which existed only because the caller already held the object, so a coverage audit that greps for one spelling reports coverage it never checked; the reliable signal was the function signature, since the gate needs a dependency the ungated function did not accept, and that is visible without reading a line of the body.

The third, where it is possible, is to check the gate at the exit. Applied by hand at each call site, coverage becomes a property of the author's memory, whereas a filter that content cannot structurally avoid, applied where results are serialized, cannot be missed on a new path. That is a larger refactor than a bug fix and I did not propose it, but it would stop the next new method shipping without a check. Underneath all three is the trust model, which is worth settling before anyone argues about severity: most of the disagreement in this finding was about whether lockdown was a boundary or a filter, and the code read the same either way, so getting the trust model written into the docs was the most useful outcome of the report.

# the release that shipped it

for t in v1.6.0 v1.7.0 v1.8.0 v1.9.0; do

    --jq .content | base64 -d \
    | grep -nE 'func GetPullRequestCommits|enforcePullRequestLockdown'
done
